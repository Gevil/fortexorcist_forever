# ForteXorcist v1.980.8 — Reference Functional Spec

Machine-readable functional law of the original, extracted from the shipped source under
`/tmp/fxref`. Behaviour-focused: every entry has source anchors (`file:line`), a Forever
feasibility verdict, and the closest Forever-legal equivalent. Visual defaults are **not**
re-derived here (PLAN §3.5 owns them); this file owns **behaviour and the option surface**.

Verdict vocabulary (exactly these four):

| Label | Meaning |
|---|---|
| `feasible-as-is` | The mechanism's inputs are all plain and legal on Forever at the same moment |
| `feasible-via-cast-prediction` | Own-cast events drive it in combat; a plain (out-of-combat) read re-anchors it |
| `feasible-out-of-combat-only` | Needs an aura/unit read that is secret-blocked in combat; legal out of combat |
| `NOT-feasible-on-Forever` | Needs the combat log, an enemy/other-player in-combat aura read, or a removed API |

Anchor base: all paths relative to `/tmp/fxref/`. `CD` = Forte_Cooldown, `ST` = Forte_Timer,
`CA` = Forte_Casting, `SS` = Forte_Soulstone, `HS` = Forte_Healthstone, `SU` = Forte_Summon.

## 0. Provenance and corpus

- Every Lua file's line 1 is the same banner:
  `--ForteXorcist v1.980.8 by Xus 28-09-2012 for 5.0` (`Forte_Core/Forte_Core.lua:1`,
  `Forte_Cooldown/Forte_Cooldown.lua:1`, `Forte_Timer/Forte_Timer.lua:1`, …).
- TOCs declare `Interface: 50001`, author `Xus (Xussie of Kazzak EU)`,
  `Dependencies: Forte_Core` (`Forte_Cooldown/Forte_Cooldown.toc:1-7`;
  `Forte_Class/Forte_Class.toc` lists `OptionalDeps: Forte_Casting, Forte_Timer, Forte_Cooldown`
  and 12 class folders incl. `Monk`, `Vehicle`).
- **Era tension (source-level):** the shipped code is MoP-era (5.0.1 spell IDs such as
  `111859` Grimoire: Imp, `114153` Divine Intervention, `113746` Weakened Armor) while its *event and
  API surface is Burning-Crusade-era*: `UNIT_SPELLCAST_SENT/START/SUCCEEDED/DELAYED/FAILED/INTERRUPTED`,
  `UNIT_SPELLCAST_CHANNEL_START/UPDATE/STOP`, `COMBAT_LOG_EVENT_UNFILTERED`, `UnitAura`,
  `UnitBuff`, `GetSpellCooldown`, `GetItemCooldown`, `GetPetActionCooldown`, `GetWeaponEnchantInfo`,
  `GetTotemInfo`, `PLAYER_TOTEM_UPDATE`, `GetRaidRosterInfo`, `IsInGroup`, `IsInRaid`,
  `ShapeshiftForm`, `GetGlyphLink`, `SendAddonMessage`, `RegisterAddonMessagePrefix`,
  `ChatFrame_AddMessageEventFilter`, `SetOverrideBindingClick`, `hooksecurefunc`,
  `DEFAULT_CHAT_FRAME:AddMessage`. Treat it as **historical reference law, never as portable code**.
- `Forte_Cooldown/Forte_Cooldown.toc` lists `Register.lua` as a shipped file, and
  `Forte_Cooldown/Register.lua` is **absent from this extract** (verified: no such file). Consequence:
  the shipped Cooldown module's *data* (the per-spell/item registration table: which spells are
  tracked, their category, hidden-CD values for trinkets/enchants) is not in the corpus. The
  mechanism law is fully recoverable (§1); the concrete MoP item list is not. `[INFERENCE]`
- Module split is a real add-on split: Forte_Core is a hard dependency (`Dependencies:`) and owns
  the event loop, frames, options, comms; every other module is a satellite that registers into it.

## 2. Forte_Casting — the cast engine

Everything downstream (timers, messages, summon queue) hangs off one in-memory cast queue. This is
the module that proves the FX design is compatible with cast-prediction: **its own author already
built the system on self-cast events + a later plain aura check**, and used the combat log *only*
for the extras that events cannot express.

## 11. The ten most surprising behaviours (with anchors)

1. **The original is already a cast-prediction engine.** `UNIT_SPELLCAST_SUCCEEDED` does *not*
   create a timer; it sets `state=1, checkAt = now + 0.2 s` and a deferred pass fires the callbacks
   (`Forte_Casting.lua:508-545`, `:481-506`, `:584-608`), with a 3 s no-cast garbage flush
   (`:602-617`). The design we are adopting on Forever constraints is the design Xus shipped in 2012.
2. **`guid == ""` is an explicit "uncertain" marker**, resolved later by expiry-window matching
   (`|aura.expire − row.expire| < 1.5 s`) which *adopts* the predicted row (`Forte_Timer.lua:1147-1204`).
   A prediction/observation merge law, already written, with the tolerance as a user option
   (`maxlag`, hard-coded).
3. **A shorter remaining time means "refresh", a longer one means "extend".** (`Forte_Timer.lua:1190-1204`)
   — and the target-debuff scan deletes its own row when a debuff reads *shorter*
   (`Forte_Timer.lua:1250-1258`). The refresh/clip legibility rule, stated in 4 lines.
4. **Cooldown acquisition is 100 % polling of the engine's own getters, throttled by its dirty
   events** — action bars 1..120, spell book, bags 0..4, pet bar 1..10, equipped 1..19, own auras —
   with `applies/enabled == 1` as the validity gate, and the author's own bug notes
   (`NOT WORKING CORRECTLY`, `NOT WORKING AT ALL` for the pet book: `Forte_Cooldown.lua:751`,`:773`).
   No cast-event path for item/pet/actionbar cooldowns exists at all (`:651-784`, `:1560-1571`).
5. **Hidden cooldowns:** a *buff* presence synthesises a cooldown that started when the buff did
   (`CD:AddHiddenCooldown(item,buff,seconds)` + `CD:CheckCooldown(spell, expire-duration, hiddencd, …)`),
   ~60 shipped trinket/enchant rows (`Forte_Cooldown.lua:149-154`, `:812-826`, `:1619-1656`). A proc is
   a cooldown — the idea modern cooldown managers rediscovered.
6. **The bar's clock is interpolated, not the clock.** `st[i][20] += (st[i][1]-st[i][20])/TimerSmooth`
   plus a re-anchored `now2 = max(now, expire − duration)` and `minDuration = max(1, now2+5-min)`
   (`Forte_Timer.lua:1045`, `:1930-1948`) — the "TimerSmooth" feel is a filter on the *display* clock,
   never on the data.
7. **Groups rotate focus on a fixed cycle.** Overlapping icons form a group, one is visible, it ramps
   over 1.5 s, then hands over (`Forte_Cooldown.lua:610-641`); a *failed cast attempt* steals focus for
   0.5 s and lights the attention spark (`:871-886`, `:1098-1112`, `:941-961`). "You just tried to cast
   this" is a first-class UI signal, driven by `UNIT_SPELLCAST_FAILED` alone.
8. **The Summon Assistant reads the world map, not the roster.** It calls `SetMapZoom(1..4)` and
   samples `GetPlayerMapPosition` per member, self-disables with a user message if the sampling takes
   >0.1 s ("conflict with a worldmap addon"), and carries a Coilfang-Reservoir coordinate hack plus a
   "BLIZZARD FAILS … someone in your instance outside viewing range shows up in some bugged spot"
   comment (`Forte_Summon.lua:193-215`, `:216-241`).
9. **Raid-wide state is comms, not spying.** Soulstone/Healthstone/shard/version data are FX2
   request/reply pairs (`SYQ`/`SYR T …|…|…`, `HG`/`HS`, 10 s staleness guard, offline timers paused,
   reboot ⇒ wipe all shared state) — `Forte_Soulstone.lua:438-497`, `Forte_Core.lua:951-973`,
   `:2026-2033`. FX **never** read other players' auras: the aura scan is explicitly
   `isMine = {player,pet,vehicle}` filtered (`Forte_Timer.lua:1095`).
10. **Two advertised features are not in the shipped source.** The Cooldown Timer's swing/auto-attack
    mode exists only as `Swing = false` + an option + a design note
    (`Forte_Cooldown.lua:60-73`, `:1705-1706`, `:1823`), and multi-charge display does not exist
    ("charges" = `GetWeaponEnchantInfo` enchant charges only, `:829-831`). Also: Forte_Talent is
    commented out end-to-end with a red "disabled" line in its own options
    (`Forte_Talent.lua:6-367`, `:368-373`), and Forte_Cooldown's TOC references a `Register.lua` that
    is not in the extract (its MoP item/spell data surface).
